# AI Sana frontend

Клиентская часть демонстрационной платформы AI Sana. Бизнес создаёт и публикует задачи, команда находит их, отправляет предложение и сдаёт результат этапа.

Этапы T001–T003 готовы. Приложение включает общую оболочку, четыре маршрута, переключение демопользователя, типизированный API-клиент, каталог опубликованных задач, публичные подробности и отправку предложения командой. Конструктор и кабинеты пока представлены только маршрутами оболочки.

## Стек

- React 19
- TypeScript
- Vite
- React Router
- Manrope Variable через локальный пакет `@fontsource-variable/manrope`

Backend находится вне этой папки и разрабатывается отдельно. Frontend не хранит данные, не рассчитывает рейтинг задачи и не начисляет баллы команды.

## Требования

- Node.js с поддержкой Vite 8
- npm
- доступный backend AI Sana

Проверенная локальная среда: Node.js 24 и npm 11.

## Установка

```bash
cd frontend
npm install
```

## Переменные окружения

Скопируйте пример конфигурации:

```bash
cp .env.example .env
```

Для Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

Доступная переменная:

```dotenv
VITE_API_BASE_URL=http://localhost:8000
```

Если переменная не задана, клиент использует `http://localhost:8000`.

Все переменные с префиксом `VITE_` попадают в браузерную сборку. Не помещайте туда API-ключ AI, токены и другие серверные секреты. Frontend обращается только к backend AI Sana, а backend выполняет вызовы AI со своим ключом.

## Маршруты

| URL | Раздел |
|---|---|
| `/catalog` | Каталог опубликованных задач |
| `/catalog/:taskId` | Публичная карточка опубликованной задачи |
| `/constructor` | Конструктор задачи |
| `/business` | Кабинет бизнеса |
| `/team` | Кабинет команды |

Переходы работают на клиенте без полной перезагрузки страницы. Неизвестный маршрут перенаправляет в каталог.

## Каталог задач

Реализация находится в `src/features/catalog/`:

- `CatalogPage.tsx` загружает список, управляет фильтрами, сортировкой и состояниями запроса.
- `TaskDetailsPage.tsx` показывает подтверждённые поля и расшифровку рейтинга.
- `catalog.css` содержит desktop-first компоновку списка, фильтров и подробностей.

### Загрузка данных

Каталог вызывает `api.catalog()`, то есть `GET /api/tasks`, после появления выбранной демоидентичности. Каждый защищённый запрос получает текущий `X-Demo-Identity` из `DemoSession`.

Backend по контракту возвращает только опубликованные задачи в `{ \"items\": [...] }`. Frontend дополнительно исключает элементы с `published: false`, чтобы черновик не появился в публичном списке при ошибочном ответе интеграции. Список не содержит локальных демонстрационных задач и не подменяет ответ API.

При смене демопользователя создаётся API-клиент с новым ID, после чего каталог загружается повторно. Устаревший ответ предыдущего запроса не записывается в состояние после размонтирования эффекта.

### Фильтры и сортировка

Фильтры работают над актуальным списком, полученным от backend:

- `topic` выбирает точное значение темы;
- `level` принимает `draft`, `working`, `ready` или `priority`;
- `sort=asc` сортирует рейтинг по возрастанию;
- отсутствие `sort` означает рейтинг по убыванию.

Значения хранятся в query string. Например:

```text
/catalog?topic=HR&level=working&sort=asc
```

Ссылка на задачу переносит query string на `/catalog/:taskId`, а действие `Назад в каталог` возвращает пользователя к тем же фильтрам. Кнопка `Сбросить фильтры` очищает параметры и возвращает сортировку по убыванию.

Темы для списка выбора строятся из непустых `topic` текущего ответа API и сортируются по русской локали. Frontend не создаёт темы, уровни готовности или рейтинг самостоятельно.

### Публичная карточка

Экран `/catalog/:taskId` намеренно получает задачу повторным вызовом `GET /api/tasks` и ищет её среди опубликованных элементов. Не заменяйте этот запрос на `GET /api/tasks/{id}` без изменения backend-контракта.

Причина: владелец задачи получает через `GET /api/tasks/{id}` текущую редактируемую версию. В ней могут быть неподтверждённые изменения. Каталог всегда возвращает опубликованный снимок, поэтому публичный экран не раскрывает незавершённые правки владельца.

Карточка показывает:

- название и тему;
- контекст и потребность;
- пользователей;
- данные и материалы;
- ограничения;
- ожидаемый результат;
- критерии успеха;
- контакт;
- консультации и обратную связь;
- итоговый рейтинг, уровень готовности, категории, основания начислений и недостающие сведения.

Пустое подтверждённое поле отображается как `Не указано`. Это состояние неизвестного значения, а не сгенерированный факт.

### Состояния интерфейса

- Во время запроса отображаются строки загрузки с `aria-busy=true`.
- Пустой ответ показывает отдельное состояние без выдуманных задач.
- Нулевая выборка после фильтра объясняет, что нужно изменить или сбросить фильтры.
- Ошибка API показывает `message` из `ApiError` и кнопку повторной загрузки.
- Повторная загрузка использует тот же API-клиент и текущую демоидентичность.
- Неизвестный или снятый с публикации `taskId` показывает состояние `Опубликованная задача не найдена`.

Карточки списка являются строками, а не источником данных для подробностей. Экран подробностей всегда повторно проверяет опубликованный снимок через API.

## Отправка предложения

Реализация находится в `src/features/proposals/ProposalPanel.tsx`, стили в `src/features/proposals/proposal.css`. `TaskDetailsPage` подключает панель после подтверждённой карточки и рейтинга.

### Доступ по роли

Панель отображается только для демоидентичности с `role: "team"`. Бизнес видит публичные подробности без формы предложения. При смене роли компонент использует новый API-клиент из `DemoSession` и повторно проверяет данные команды.

Рейтинг задачи не блокирует форму. Опубликованная задача с уровнем `draft` и рейтингом ниже 40 принимает предложение так же, как задача с более высоким рейтингом.

### Проверка существующего предложения

Перед показом формы frontend вызывает `GET /api/team/proposals` и ищет предложение текущей команды по `task_id`. Это нужно для восстановления состояния после обновления страницы и для защиты от повторной отправки по той же задаче.

Если предложение найдено, вместо формы отображаются:

- текущий статус `pending`, `selected` или `rejected`;
- идея;
- план;
- срок;
- ссылка на прототип.

Если проверка предложений завершилась ошибкой, форма не показывается. Пользователь получает сообщение и кнопку повтора. Это не даёт случайно создать дубликат, когда frontend не знает, существует ли запись на backend.

### Форма

`POST /api/tasks/{id}/proposals` получает:

```json
{
  "idea": "QR-учёт возвратной тары",
  "plan": "Собрать прототип и провести пилот",
  "duration": "3 недели",
  "prototype_url": "https://prototype.example/demo"
}
```

Поля `idea`, `plan` и `duration` обязательны. `prototype_url` необязателен, но браузер проверяет формат URL, если поле заполнено. Перед запросом frontend убирает пробелы в начале и конце значений.

Локальная проверка не отправляет пустые обязательные поля и показывает ошибку рядом с каждым полем. `ApiError.fieldErrors` из backend также связывается с соответствующим полем. Общая ошибка отображается над формой. Ни полевая, ни общая ошибка не очищает введённые значения.

### Защита отправки

Во время запроса `fieldset` и кнопка отключаются, текст кнопки меняется на `Отправляем…`. Компонент использует синхронный `submitLock` через `useRef`, поэтому два события submit в одном кадре создают один POST даже до следующего React render. Одного `disabled` для этого недостаточно.

После успешного POST ответ backend сразу становится источником блока `Ваше предложение`. После обновления страницы тот же блок восстанавливается через `GET /api/team/proposals`; локальная копия не используется как постоянное хранилище.

Если понадобится разрешить несколько предложений одной команды по одной задаче, сначала нужно изменить продуктовый контракт и правила backend. Текущий интерфейс считает найденное по `task_id` предложение активным и не показывает вторую форму.

## Демоидентичность

При старте приложение запрашивает `GET /api/demo-identities`. Ответ должен быть массивом:

```json
[
  {
    "id": "business-demo",
    "name": "ООО Ромашка",
    "role": "business",
    "team_id": null
  },
  {
    "id": "team-alpha",
    "name": "Команда Альфа",
    "role": "team",
    "team_id": "team-alpha"
  }
]
```

Выбранный ID сохраняется в `localStorage` под ключом `ai-sana.demo-identity`. Защищённые запросы отправляют заголовок:

```http
X-Demo-Identity: team-alpha
```

Роль не отправляется отдельным заголовком. Backend определяет её по ID. Это деморежим, а не production-аутентификация.

Если список идентичностей не загрузился, оболочка остаётся доступной и показывает действие `Повторить`. Пустой список блокирует переключатель без подстановки выдуманного пользователя.

## API-клиент

Типы контракта находятся в `src/api/types.ts`, клиент в `src/api/client.ts`.

Поддержаны методы для маршрутов:

- `GET /api/demo-identities`
- `POST /api/tasks`
- `GET /api/tasks/{id}`
- `PATCH /api/tasks/{id}`
- `POST /api/tasks/{id}/questions`
- `POST /api/tasks/{id}/compose`
- `POST /api/tasks/{id}/confirm`
- `POST /api/tasks/{id}/publish`
- `GET /api/tasks`
- `GET /api/business/tasks`
- `POST /api/tasks/{id}/proposals`
- `GET /api/tasks/{id}/proposals`
- `POST /api/proposals/{id}/decision`
- `GET /api/team/proposals`
- `POST /api/proposals/{id}/milestone`
- `POST /api/milestones/{id}/review`

Ошибочный ответ backend имеет форму:

```json
{
  "code": "confirmation_required",
  "message": "Сначала подтвердите задачу",
  "field_errors": {
    "title": "Заполните название"
  }
}
```

Клиент преобразует такой ответ в `ApiError` и сохраняет HTTP-статус, `code`, текст сообщения и `fieldErrors`. Если backend вернул не JSON, клиент сообщает об ошибке ответа вместо ложного успешного результата.

## Проверка интеграции

1. Запустите backend на URL из `VITE_API_BASE_URL`.
2. Выполните `npm run dev`.
3. Откройте `/catalog` и дождитесь списка опубликованных задач.
4. Проверьте сортировку рейтинга в обоих направлениях.
5. Примените тему и уровень готовности вместе, затем сбросьте фильтры.
6. Откройте `/catalog/:taskId` и сравните поля и рейтинг с опубликованным снимком API.
7. Под ролью команды откройте опубликованную задачу с рейтингом ниже 40.
8. Отправьте предложение с идеей, планом, сроком и ссылкой. Во время запроса кнопка должна быть отключена.
9. Дважды вызовите submit во время одного запроса и убедитесь по Network, что ушёл один POST.
10. Вызовите полевую и общую ошибки backend. Значения формы должны сохраниться.
11. После успешной отправки обновите страницу. Предложение должно восстановиться через `GET /api/team/proposals`.
12. Переключитесь на роль бизнеса. Панель предложения команды должна исчезнуть.
13. Проверьте ответы каталога `{ "items": [] }` и ошибку API с повторной загрузкой.
14. Выполните `npm run build` перед передачей изменений.

## Границы frontend

- Не добавлять клиентскую регистрацию.
- Не вызывать сторонний AI API из браузера.
- Не рассчитывать рейтинг задачи или баллы команды на клиенте.
- Не хранить серверные секреты в `.env` frontend.
- Не заменять данные backend статическими счётчиками перед сдачей.
- Тексты и демоданные согласовывать с QA/content.
