# Передача frontend и финальная приёмка

## Состав веток

На момент проверки локальная `integration/frontend-launch` указывает на `36de00c` и уже содержит `882c69b` и `11ac613`. В ней есть `frontend`, `backend` и `fixtures`. Переносить `882c69b` повторно не требуется.

Новые аккаунты, API 1.2 и исправления compose подготовлены в ветке `backend-mvp`. Они ещё не перенесены в integration и main. Соседняя рабочая копия integration не изменялась. Финальная версия не объявлена готовой к сдаче до завершения экранов и браузерного QA.

Текущий backend прошёл 58 тестов и отдельный HTTP-сценарий через Uvicorn с реальными аккаунтами. Это готовность backend к подключению экранов, не финальная браузерная приёмка.

## Что подключить другу

Контракт с примерами запросов: [ACCOUNTS.md](ACCOUNTS.md). Схема всего API: [openapi.json](openapi.json).

1. Регистрация/вход через `/api/auth/*`, HttpOnly-cookie и `credentials: include`.
2. При загрузке страницы восстанавливать `/api/auth/session`, хранить CSRF-токен только в памяти, добавлять его к изменяющим запросам.
3. Личный профиль брать из `/api/users/me`, профиль бизнеса/команды из `/api/profiles/me`. Email для входа не публиковать.
4. Проверять владение по `session.user.profile.id`. Кнопки роли скрывать для удобства; окончательную проверку выполняет сервер.
5. После выхода или смены пользователя очищать его состояние/черновики. Черновики привязывать к идентификатору профиля и задаче.
6. Учесть `milestone`, `team_points`, `X-AI-Source` и 422 `unassigned_answers` при сборке карточки. При 422 сохранить ответы в форме и показать `field_errors`.
7. В обычном режиме убрать выбор `X-Demo-Identity`. Для старого frontend до подключения аккаунтов доступен явно включаемый `DEMO_MODE=true`.

Восстановление пароля по email и приглашение участников пока не реализованы. Не показывать их как работающие действия.

## Порядок итоговой интеграции

После готовности frontend объединить актуальную ветку backend-mvp и frontend в `integration/frontend-launch`, не заменяя файлы frontend старой копией. Если появятся конфликты контрактов, разрешить их по API 1.2 и заново выполнить проверки. Не переносить всю ветку в main до приёмки.

В итоговой рабочей копии проверить:

```powershell
git status --short
git merge-base --is-ancestor 882c69b HEAD
git ls-tree --name-only HEAD
py -m unittest discover -s backend -t .
```

Первые команды должны подтвердить сохранённое состояние, наличие нужного предка и папок `backend`, `frontend`, `fixtures`. Затем в `frontend` выполнить `npm ci` и `npm run build`. Сверить frontend-клиент с актуальным OpenAPI, а не только с прежним отчётом QA.

## Сценарий показа до пяти минут

До показа подготовить отдельную SQLite-базу, загрузить пять демонстрационных карточек через `python -m backend.seed`, зарегистрировать бизнес и команду. Открыть их в двух отдельных профилях браузера, чтобы cookie не заменяли друг друга. Использовать только синтетические сведения. При отсутствии нового AI-ключа честно показывать fallback.

1. **0:00–0:45.** Бизнес вводит «Обращения теряются между отделами» в потребность. Показать не менее трёх уточняющих вопросов.
2. **0:45–2:00.** Ответить: операторы поддержки; синтетические CSV; прототип маршрутизации; точность 90%; две недели без персональных данных. Заполнить контекст, контакт и еженедельный созвон. Показать редактируемую карточку и источник AI.
3. **2:00–2:45.** Вручную подтвердить, показать рейтинг и его категории, опубликовать. Показать позицию в каталоге и фильтры. Низкий рейтинг также не должен блокировать публикацию подтверждённой задачи и отклики.
4. **2:45–3:30.** Команда открывает каталог, отправляет идею, план, срок и ссылку. После обновления страницы отклик остаётся pending.
5. **3:30–4:15.** Бизнес просматривает профиль команды и вручную выбирает её. Другие предложения не выбираются и не отклоняются автоматически.
6. **4:15–5:00.** Команда отправляет этап со ссылкой; бизнес подтверждает. Показать 10 баллов, повторное подтверждение не увеличивает их.

## Обязательное браузерное QA после объединения

- Регистрация обеих ролей, вход, обновление страницы, профиль, редактирование и выход; после выхода изменение данных получает 401.
- Полный сценарий выше без Swagger; отсутствие ошибок консоли и несоответствий API.
- Другой бизнес не изменяет чужую задачу, команда не изменяет чужой отклик/этап; роль и баллы нельзя повысить через запрос.
- Правка снимает подтверждение только при изменении данных. До повторной публикации каталог показывает старую карточку.
- Пустой compose и повтор ответа сохраняют состояние; нераспознанный ответ показывает 422 без потери введённого текста.
- Выбор нескольких команд и отказ всем; возвращённый этап пересдаётся, повторное подтверждение не удваивает баллы.
- Ошибки входа, 401, 403, 422, 429, отказ AI и восстановление состояния после обновления страницы отображаются понятно.

## Ключ в истории

Удаление секрета из текущих файлов не отзывает опубликованный ключ. Владелец должен отозвать его у провайдера и выпустить новый. До этого повторно не использовать старый ключ для QA. После отзыва отдельно согласовать очистку истории со всеми участниками, поскольку переписывание веток затронет их локальные копии. Эта работа не выполняет отзыв или переписывание истории и не утверждает, что риск закрыт.
