# AI Sana backend

## Сверка backend-плана и ТЗ, 2026-09-23

Итог: backend частично соответствует требованиям, но не готов к сдаче без исправлений ниже. Старые записи «проверено» относятся только к отдельным сценариям, не ко всему пункту ТЗ. Аудит не менял бизнес-логику. Проверена текущая рабочая копия `backend-mvp`, не другие ветки участников.

Метод: чтение исходников и контракта, выполнение API-сценариев через FastAPI TestClient на отдельной временной SQLite, повторный запуск приложения на той же базе. `py -m unittest backend.test_tasks` прошёл. Реальное качество ответов OpenAI, сетевой перезапуск процесса, frontend и демонстрация на защите в этом аудите не проверялись. Ключи и пользовательская база не изменялись.

### 1. Карточки задач

- Соответствует: все 11 полей, владелец, редактирование, ручное подтверждение, отдельная публикация и рейтинг.
- Проверено: черновик не доступен команде; чужая правка запрещена; публикация без подтверждения даёт 409; правки и повторное подтверждение не меняют публичный снимок; новое подтверждение после удаления сведений снижает рейтинг; повторная публикация обновляет снимок.
- Проверено: опубликованная карточка с рейтингом 0 видна команде и принимает отклик.
- Свободное описание передаётся в `context` или `need`, как указано в корневом README. Отдельного `description` нет. Запрос с неизвестным `description` принимается и молча теряет этот текст. Само отсутствие отдельного поля не нарушает ТЗ, но молчаливую потерю ввода нужно устранить и согласовать с frontend.
- Исторические версии сверх текущего и опубликованного снимков не требуются планом. Их отсутствие не является дефектом.

### 2. AI

- Есть OpenAI-клиент, серверные переменные окружения, промпты, JSON-вход/выход, таймаут, обработка ошибок провайдера и структуры с локальным fallback. Подтверждение, публикация, рейтинг и выбор команд модели не передаются.
- Сборка проверяет наличие всех строковых полей и совпадение новых значений с подстроками исходных сведений. Это защита от новых текстовых фактов, но не доказательство правильного смысла: извлечение части отрицания или неверная классификация всё ещё возможны.
- Воспроизведено: когда отсутствуют только ограничения, локальный режим спрашивает про уже заполненные контекст, потребность, пользователей, данные и успех; про ограничения не спрашивает.
- Воспроизведено: локальный compose не заполняет контакт по вопросу «Какой контакт?» и ответу `mail@example.com`. Таблица сопоставления не охватывает title, topic, contact, consultation.
- Воспроизведено на имитированном ответе модели: `["A","A","A","A","A","B","C"]` проходит проверку, затем обрезается до пяти одинаковых вопросов. Минимум три разных уместных вопроса не гарантируется.
- Реальный успешный вызов OpenAI не доказан этим аудитом; наличие адаптера не равно работоспособному ключу/балансу.
- Происхождение заполненных полей и отдельные рекомендации «Что мешает начать?» отсутствуют. Это явно вторичный приоритет backend-плана, не блокер основного сценария.
- Локальная заглушка разрешена исходным ТЗ при недоступности внешнего API, но должна оставаться полезной. Отсутствие работающего внешнего API само по себе не означает провал ТЗ при качественной заглушке.

### 3. Рейтинг

- Соответствует по коду: веса 20/20/15/15/10/10/10, уровни 0–39/40–69/70–89/90–100, серверная формула, баллы только подтверждённым сведениям, categories/basis/missing.
- Проверено: пробельные значения дают 0; удаление сведений после подтверждения уменьшает баллы.
- Воспроизведено: «10 заявок за 7 дней» получает 0 за критерии, «точность 90%» получает 15, «kpi 1» получает 15. Текущая проверка цифры и маркера пропускает бессодержательные строки и не распознаёт часть измеримых русских формулировок.
- Контекст/потребность оцениваются по 10 за строку, контакт/consultation по 5. Наличие содержательного порядка обратной связи отдельно не проверяется. Для MVP нужны согласованные проверяемые правила; документирование эвристики не доказывает согласование с коллегами.
- Название, тема, известность бизнеса и персональные признаки на рейтинг не влияют.

### 4. Каталог и предложения

- Проверено: рейтинг 0 не блокирует каталог и отклик, фильтры темы/уровня возвращают такую задачу, выбор первой команды оставляет вторую pending, затем можно выбрать обе.
- По коду: сортировка по опубликованному рейтингу; нет искусственного лимита числа откликов; есть идея, план, срок, ссылка и team_id; статусы pending/selected/rejected; выбор только вручную владельцем.
- Воспроизведено: идея, план и срок из одних пробелов принимаются с HTTP 200. Ссылки не валидируются и могут отсутствовать. ТЗ требует возможность передать ссылку, но не однозначно требует готовый прототип для каждого первого отклика; обязательность согласовать, URL-валидацию исправить.
- Неизвестный level сейчас даёт пустой список, а не ошибку валидации. В контракте следует точно закрепить поведение.
- Список предложений доступен всем командам, а не только автору/бизнесу. ТЗ не задаёт приватность откликов явно; это решение контракта, не доказанное нарушение.

### 5. Этап и баллы

- Проверено: команда не может подтвердить свой результат (403); повторное подтверждение того же этапа оставляет 10 баллов.
- Критическая ошибка, воспроизведено: повторная отправка по одному выбранному предложению создаёт другой этап; подтверждение двух этапов сохраняет 20 баллов. Это нарушает правило backend-плана «один этап на принятое предложение».
- Воспроизведено: возврат без комментария принимается (200); changes_requested можно подтвердить без пересдачи (200); результат можно подтвердить после перевода предложения в rejected (200).
- По коду: пересдача создаёт новую запись, а не обновляет возвращённый этап. Нужна явная таблица допустимых переходов и атомарная обработка.
- Через списки предложений не возвращаются этап, комментарий проверки и баллы; отдельного GET этапа или суммы баллов команды нет. Фактически баллы есть только в записи milestone. Это мешает восстановить кабинеты после перезагрузки страницы без сохранённых на клиенте ответов POST.
- Число 10 является решением backend-плана, не обязательной цифрой общего ТЗ. Один этап также ограничение нашего плана; общий ТЗ допускает баллы за фактический подтверждённый прогресс.

### Контракт, исходные данные и сдача

- Все 16 маршрутов предложенного API присутствуют. Демоидентичность: X-Demo-Identity, без production-регистрации. В коде один бизнес и две команды.
- Недостаток данных: нет каталога fixtures или команды seed; нет подготовленных пяти черновиков, пяти карточек, пяти профилей с интересами/навыками/технологиями и пяти откликов. Две команды без профилей не заменяют требуемый набор.
- Ошибки бизнес-правил и Pydantic имеют code/message/field_errors, но неизвестный маршрут возвращает `{"detail":"Not Found"}`. Общий формат реализован не для всех ошибок.
- CONTRACT.md ошибочно закрепляет пересдачу новым milestone, противореча backend-плану. Есть неточные примеры рейтинга и неполное описание list-ответов. Большинство endpoint имеют response type dict, поэтому Swagger не показывает точную схему успешного ответа.
- Документ с контрактом есть, но факт согласования frontend/QA и уведомления об изменениях не подтверждён.
- Корневой README уже содержит архитектуру, формулу и сценарий, однако утверждение «внешняя AI-модель не подключена» устарело относительно адаптера. Файл принадлежит QA, в этом аудите не редактировался; QA нужно обновить описание OpenAI и ограничений.
- Запуск backend описан; повторный lifespan сохранил опубликованную задачу и баллы. Хранение ошибочно начисленных баллов тоже сохраняется: persistence не доказывает правильность бизнес-правил.
- В этой рабочей копии frontend отсутствует. Это не задача backend-разработчика; состояние других веток не проверено. Сквозная демонстрация через веб-интерфейс и запуск экспертом не подтверждены.
- Полноценная регистрация, чат, уведомления, ML-обучение, векторная БД, мобильная адаптация и production-инфраструктура не требуются. Их отсутствие не считаем недоработкой.
- Соблюдение пятичасового расписания, распределение ролей и демонстрация до пяти минут не доказываются наличием кода. Численную оценку из 100 по этому аудиту не назначаем.

### Порядок дальнейшей работы

Продолжать по backend-плану, по одному пункту с воспроизведением, исправлением, проверкой и отдельным отчётом: AI → рейтинг → каталог/предложения → этап/баллы → демоданные и контракт с QA/frontend → сквозная проверка и инструкция. Пункт карточек проверен регрессией; молчаливые неизвестные поля нужно закрыть при согласовании входного контракта. Никаких дополнительных функций до устранения обязательных дефектов.

## Run

From repository root on Windows:

```powershell
py -m pip install -r backend/requirements.txt
py -m uvicorn backend.main:app --reload --port 8000
```

SQLite is stored in `backend/sana.sqlite3`. Set `DATABASE_PATH` to use another file. The database is created on startup. Delete that file to reset demo data.

Use `X-Demo-Identity` on every API call. Valid values and roles are returned by `GET /api/demo-identities`.

The full JSON contract is in [`CONTRACT.md`](CONTRACT.md). FastAPI docs are available at `http://localhost:8000/docs`.

## Smoke request

```powershell
$headers = @{ "X-Demo-Identity" = "business-demo" }
Invoke-RestMethod http://localhost:8000/api/demo-identities
Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/tasks -Headers $headers -ContentType "application/json" -Body '{"title":"Проблема","context":"Контекст","need":"Потребность"}'
```

## OpenAI

Создайте `.env` в корне репозитория по образцу `.env.example`:

```dotenv
AI_API_KEY=ваш_ключ
AI_MODEL=gpt-4o-mini
AI_BASE_URL=https://api.openai.com/v1
AI_TIMEOUT_SECONDS=15
```

`.env` исключён из Git. Не передавайте ключ frontend и не добавляйте его в отчёты.
Перезапустите сервер после изменения `.env`. Переменные процесса имеют приоритет над файлом.

`POST /api/tasks/{id}/questions` передаёт текущие поля и список отсутствующих полей.
Ответ модели: `{"questions":["Вопрос 1","Вопрос 2","Вопрос 3"]}`.
`POST /api/tasks/{id}/compose` передаёт текущие поля и массив `answers`.
Ответ модели должен содержать все 11 строковых полей карточки; неизвестное остаётся пустым.
Промпты находятся в `backend/ai.py`. Сборка использует извлечение цитат, а не свободное перефразирование: новые значения сверяются с текстом пользователя. Это ограничивает выдуманные значения, но не гарантирует правильную смысловую классификацию; человек проверяет карточку.

Без ключа, при ошибке OpenAI, таймауте или неверном JSON используется локальный режим. Формат API не меняется; в ответе пока нет признака использования fallback. Рейтинг, подтверждение и публикация не делегируются модели.
