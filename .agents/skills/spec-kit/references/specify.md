# Spec Kit: specify

Создай или уточни `spec.md`. Принимай описание обычным языком. Здесь нужен результат и его смысл, не способ реализации.

## Определи действие

По правилам `SKILL.md` отличи новое изменение от уточнения существующего. Для нового не подставляй ранее выбранную или единственную найденную папку. Если по указанному пути ещё нет spec, это создание новой спецификации, а не способ обойти интервью.

Для уточнения выбери существующий workspace. Разреши неоднозначность до записи.

Пустой файл или незаполненный шаблон не считается существующей spec и тоже требует интервью до заполнения.

Прочитай запрос, инструкции проекта и только тот код или документацию, которые помогают понять поведение и ограничения. При уточнении также прочитай текущую spec и связанные `plan.md` и `tasks.md`. Не задавай вопросы, на которые отвечает репозиторий. Не меняй код проекта.

## Новая spec: обязательное интервью

Правила grilling встроены в этот раздел. Не вызывай отдельный скилл, не проверяй его установку и не загружай внешние инструкции. Этот этап нужен только для новой спецификации. Для существующей переходи к разделу уточнения ниже.

Пока остаются незакрытые вопросы или пользователь ещё не подтвердил итоговые договорённости явно, не создавай папку изменения, `spec.md`, черновик, отдельный файл интервью или другие артефакты. Разрешены только исследование и разговор с пользователем. Запрос полного цикла или batch не отменяет этого правила.

1. Построй дерево существенных решений. Проверь цель, потребителя результата, ожидаемое поведение, границы, важные ограничения, спорные сценарии и критерии приёмки. Включай только ветки, способные изменить требования. Архитектурные решения без влияния на требуемый результат оставь плану.
2. Закрой фактические вопросы чтением проекта. Учитывай ответы, уже данные пользователем. Подробное исходное описание не освобождает от финального подтверждения, но не требует повторять решённые вопросы.
3. Выбери ближайший нерешённый вопрос с учётом зависимостей. Задай строго один вопрос и дождись ответа. Вместе с ним дай рекомендуемый ответ и короткую причину. Не прячь несколько независимых решений в один вопрос и не выдавай анкету.
4. После ответа обнови дерево решений. Выбор остаётся за пользователем. Рекомендация не считается принятым решением. Если ответ выявил новый существенный вопрос, разбери его до перехода дальше. Не считай молчание, отсутствие доступа или собственное предположение ответом пользователя.
5. Когда все существенные вопросы закрыты, кратко изложи согласованный результат, требования, границы, критерии приёмки и принятые риски. Попроси явно подтвердить общее понимание и остановись до ответа. Ответ на отдельный вопрос и первоначальное разрешение работать не заменяют подтверждение этого итога.
6. Если пользователь исправил итог, вернись к затронутым решениям, затем снова представь итог для подтверждения. Если он его подтвердил, переходи к записи spec без повторного запроса того же разрешения.

Формат вопроса:

```markdown
**Вопрос:** <одно нерешённое решение>

**Моя рекомендация:** <ответ и короткая причина>
```

Нужен один связный результат. Не дроби цельную возможность ради размера. Если запрос содержит независимые изменения, сначала согласуй, какое описываем. Ответ "не входит в это изменение" закрывает вопрос только как явное решение о границах, а не как способ скрыть обязательное требование.

Если пользователь недоступен, остановись без записи. Если контекст разговора потерян, сначала восстанови доступные ответы и подтверждение. Когда это невозможно, запроси недостающее по одному вопросу. Не объявляй интервью завершённым и не выдумывай согласование.

## Запись новой spec

Этот раздел выполняется только после подтверждения итога интервью.

Прочитай `assets/SPEC-TEMPLATE.md` и подготовь согласованное содержимое. Если при подготовке обнаружился новый существенный вопрос, вернись к интервью до создания файлов. Новая spec не должна содержать нерешённых существенных вопросов или несогласованных предположений. В `Открытые вопросы` напиши `Нет.`.

Возьми текущие дату и время из окружения, выбери короткое имя в kebab-case и создай папку `ai/specs/YYYY.MM.DD_HH-MM_change-name/` файловыми инструментами. Кириллица допустима. При коллизии автоматически выбранного имени добавь `-2`, затем `-3`. Если пользователь явно указал занятый путь для нового изменения, уточни другой путь, не перезаписывая существующую папку. Создай только `spec.md`, без плана и задач.

## Уточнение существующей spec

Обязательное интервью и отдельное финальное подтверждение из раздела новой spec здесь не нужны. Выполни ясный запрос пользователя. Если для правки не хватает существенного решения, уточни его, но не начинай весь опрос заново. Нельзя выдавать независимое новое изменение за уточнение ради обхода интервью.

Не перезаписывай файл шаблоном. Сохрани ID требований, новым выдавай новые ID. Не используй освободившийся ID для другого смысла. Если требование снято по решению пользователя и на него уже есть ссылки, сохрани запись о снятии и решение.

После смыслового изменения требований прежний план и затронутые задачи нужно проверить заново. В `plan.md`, если он есть, запиши в `Риски и решения`, что устарело и почему.

В `tasks.md` сохрани прежние результаты как историю, пометь затронутые доказательства неактуальными и верни затронутые задачи в `pending` либо `blocked` с причиной. Учти зависимые задачи. Итоговое решение сбрось в `не проверено`. Редакционная правка без изменения смысла не требует сброса.

Если при уточнении обнаружился блокирующий вопрос, отметь его как `ТРЕБУЕТ УТОЧНЕНИЯ` и не переходи к плану. Это не разрешает создавать новую spec с незавершённым интервью.

## Содержание spec

Сохрани четыре раздела шаблона:

- `## Зачем`: проблема, потребитель результата и что должно измениться.
- `## Требования`: наблюдаемые правила, сценарии и ограничения с устойчивыми ID `R1`, `R2` и далее. Для каждого укажи условие и проверяемый результат.
- `## Не входит`: явные границы изменения.
- `## Открытые вопросы`: для новой согласованной spec `Нет.`; при уточнении существующей перечисли обнаруженные вопросы и их влияние.

Пиши так, чтобы spec можно было понять без чата. Не вводи приоритеты ради формальности. Пути и технические ограничения включай только там, где они сами часть требуемого результата. Выбор архитектуры и последовательность реализации оставь плану. Замени все подсказки шаблона реальным содержимым.

## Результат

После записи сообщи точный путь к `spec.md`, суть изменения и готовность к `plan`. При остановке на интервью покажи только текущий вопрос или итог для подтверждения и явно скажи, что файлы ещё не созданы.

Не переходи к следующей фазе без запроса на неё или на полный цикл. Даже при полном цикле сначала получи подтверждение итога интервью. Артефакты остаются локальными, без staging, автоматического commit и push.
