# Spec Kit

Помоги провести изменение от требований до проверенного результата. Работай обычными инструментами чтения и редактирования файлов. Установка программ и запуск служебных команд не нужны.

## Действия

| Запрос | Что сделать | Инструкция |
|---|---|---|
| `specify <описание>` | Провести интервью и согласовать новую spec; уточнить существующую | `references/specify.md` |
| `plan <workspace>` | Выбрать подход, файлы и проверки | `references/plan.md` |
| `tasks <workspace>` | Разбить план на проверяемые задачи | `references/tasks.md` |
| `implement <workspace> [T001]` | Выполнить одну задачу | `references/implement.md` |
| `verify <workspace>` | Проверить результат изменения | `references/verify.md` |
| `list` или запрос статуса | Показать работу и следующий шаг | `references/list.md` |

Это действия в чате, не команды терминала. Понимай обычные формулировки без точного синтаксиса.

- Без аргументов прочитай `references/list.md`, покажи текущую работу и предложи следующий шаг. Ничего не создавай и не запускай реализацию.
- Для явного действия прочитай только его инструкцию. Не загружай все файлы `references/` и шаблоны заранее.
- На вопрос о процессе ответь без изменения файлов.
- Для "продолжай" во время интервью используй уже полученные ответы и ближайший нерешённый вопрос. После создания spec выбирай следующий шаг по содержимому файлов.
- Полный цикл выполняй только по явному запросу. После каждого действия заново проверь готовность следующего.
- Несколько задач подряд выполняй только по явному запросу batch/YOLO, прочитав `references/batch-mode.md` вместе с implement.

## Интервью перед новой spec

Для новой спецификации обязательно встроенное интервью из `references/specify.md`. Отдельный скилл grilling не нужен. Задавай по одному существенному вопросу, кратко обосновывай предложенный ответ и жди решения пользователя.

До закрытия вопросов и явного подтверждения итоговых договорённостей не создавай workspace, spec или другие файлы. Полный цикл и batch не обходят этот этап. Даже если исходный запрос содержит все ответы, сначала представь итог для подтверждения. При уточнении существующей spec обязательное интервью не запускается.

Пока файлов нет, используй ответы текущего разговора. Не создавай отдельный файл интервью. Если ответы или подтверждение утрачены, восстанови доступный контекст либо запроси недостающее, не считай согласование состоявшимся.

## Файлы изменения

```text
ai/specs/YYYY.MM.DD_HH-MM_change-name/
  spec.md
  plan.md
  tasks.md
```

`spec.md` хранит требования и ограничения результата. `plan.md` хранит решение, границы редактирования и проверки. `tasks.md` хранит задачи, их статусы и фактические результаты проверок.

Создавай файлы по мере необходимости. Исследования и модель данных описывай в плане, результаты проверок рядом с задачами. Не создавай отдельный реестр, файл состояния или счётчики прогресса.

Пути `references/` и `assets/` отсчитывай от папки этого скилла, не от рабочего проекта. Workspace находится в проекте пользователя.

## Выбор workspace

Для `specify` сначала определи, это новое изменение или уточнение существующего. Для новой spec проведи интервью и после подтверждения создай отдельный workspace. Не используй ранее выбранную или единственную найденную папку. Повторно используй папку только при запросе на уточнение или явной связи с существующим изменением. Если намерение неясно либо для новой spec указан занятый путь, уточни выбор до записи.

Для работы с существующим workspace:

1. Используй явно указанный путь. Если дан путь к одному из трёх файлов, возьми его папку.
2. Для имени просмотри папки `ai/specs/` и найди совпадения, включая суффиксы для различения одинаковых имён.
3. Если путь не задан, используй явно выбранный пользователем workspace. Иначе просмотри список и выбери только при единственном подходящем варианте.
4. При нескольких подходящих вариантах спроси выбор. Не выбирай последний по дате молча.
5. Если ничего не найдено, предложи specify. Отсутствие `ai/specs/` нормально для нового проекта.

Не считай старые workspaces источником требований для нового изменения без указания пользователя.

## Следующий шаг

Проверяй содержимое, не только наличие файлов. Пустой шаблон не означает готовность.

| Что найдено | Следующий шаг |
|---|---|
| Нет workspace или требований | specify |
| Новая spec обсуждается, итог ещё не подтверждён | Продолжить интервью без создания файлов |
| В spec есть блокирующие вопросы | Уточнить spec |
| Spec готова, плана нет или он не закончен | plan |
| План готов, списка задач нет или он не покрывает требования | tasks |
| Есть допустимая `pending` задача | implement |
| Есть `in_progress` или блокер | Выяснить состояние и устранить блокер, не начинать повторно |
| Задачи завершены, итоговая проверка не выполнена | verify |
| Итог подтверждён актуальными проверками | Сообщить результат, не начинать новый цикл |

Явный запрос не отменяет обязательные условия. Без готовой spec не пиши план; без готового плана с границами не создавай задачи; без проверяемых задач не начинай реализацию. Verify можно вызвать раньше завершения, чтобы получить отчёт о пробелах, но не решение о готовности.

Если изменились требования или подход, проверь затронутые задачи и прежние результаты. Не используй устаревшее решение «готово» после изменения кода, требований или проверок.

Явный запрос исправить найденный дефект ведёт в implement, даже если затронутая задача уже `done` или `blocked`. Применяй правила возврата на исправление из `references/implement.md`; такой запрос не снимает внешние блокеры и ограничения плана.

## Границы работы

- Не выдумывай продуктовые решения. Сначала ищи ответ в проекте; спрашивай только о нерешённых существенных вариантах.
- В `plan.md` перечисляй, что можно менять, что требует подтверждения и что нельзя менять. Неуказанные файлы требуют подтверждения перед записью. При конфликте действует более строгое ограничение.
- Явное подтверждение пользователя запиши в план с датой и точными границами. Разрешение на одну задачу не разрешает менять всё вокруг.
- Заполнять три файла текущего workspace можно в рамках запрошенного действия. Это не разрешает молча менять согласованные требования или расширять границы реализации.
- Один исполнитель обновляет workspace. Не запускай независимые сессии на одном списке задач: Markdown не защищает от одновременной записи.
- `done` требует фактической проверки. Если обязательная проверка недоступна или падает, задача остаётся `blocked`, с причиной и следующим шагом.
- Сохраняй чужие изменения и прежние результаты. Не перезаписывай существующие файлы шаблонами.
- Файлы процесса остаются локальными. Не добавляй их в git, не обходи ignore-правила. Commit и push выполняй только по явному запросу пользователя, не после каждой задачи автоматически.
